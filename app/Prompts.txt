# Спецификация 1: управление контекстным окном — единый контекст, без субагентов

Область: только context engineering. Guard'ы цикла, grounding-валидация и контракт
ответа (`status` / `text` / `error`) описаны в основной спецификации агента и здесь
не дублируются.

---

## 1. Условия окружения

| Параметр | Значение |
|---|---|
| Модель | `kimi-k2-6`, thinking переключаемый |
| Окно `W` | 100 000 токенов, **задаётся конфигом**, может быть уменьшено |
| Поведение на лимите | Прокси возвращает **ошибку**. Тихого усечения нет. |
| Prompt caching | **Отсутствует и не появится** |
| MCP | `search_cql`, `get_section(keywords)`, `get_page` |

MCP уже выполняет пятиуровневую очистку и возвращает из таблиц только строки
с keywords. **Не дублировать эту работу.**

---

## 2. Два следствия, определяющих весь дизайн

### 2.1 Нет кэша → контекст не накапливается

Каждый токен оплачивается на каждом ходу. Стоимость сессии — это сумма размеров
контекста по всем ходам, а не размер финального контекста.

| Схема | 15 ходов | 30 ходов |
|---|---|---|
| Накопление (+3k/ход от 8k) | 53k | **98k — отказ прокси** |
| Пересборка (константа 22k) | 22k | 22k |

Deep research — это 30+ ходов. С накоплением исследование обрывается на середине,
и аварийное сжатие уже не помогает: данные для него негде взять.

Обратная сторона: переписывание префикса больше ничего не стоит. Аргумент
«не рвать кэш» исчез, сжимать можно агрессивно и каждый ход.

> **Инвариант 1. Контекст не накапливается — он пересобирается на каждом ходу
> из внешнего состояния.**

### 2.2 Ошибка на лимите → только preflight

Ошибка детерминируема и не портит контекст тихо — это хорошо. Но ловить её
ретраем нельзя: каждая попытка стоит полный round-trip.

> **Инвариант 2. Ни один запрос не отправляется без локальной проверки размера.**

---

## 3. Модель состояния

Три хранилища, все **вне контекста модели**:

```
StoredLog     append-only, полная история — аудит и отладка
ResearchLedger структурированное состояние исследования — ИСТОЧНИК ИСТИНЫ
RawStore      сырые тексты по ключу pageId+version — для перечитывания
```

Контекст одного хода собирается заново:

```
system (F)
+ исходный вопрос
+ render(ResearchLedger)
+ rawWindow — последние N результатов инструментов
+ последнее сообщение модели
```

`RawStore` критичен: он позволяет вернуть вытесненный текст в контекст без
повторного обращения к Confluence. Без него единственный способ исправить
потерю — полный повторный обход.

---

## 4. Обязательное конспектирование

Это механизм, который делает вытеснение безопасным. Без него любое сжатие — потеря.

Модели даются дополнительные инструменты:

```
record_finding(subQuestionId, claim, pageId, quote, confidence)
mark_irrelevant(pageId, reason)
open_subquestion(text) / close_subquestion(id, status)
```

**Правило принуждения:** если модель запрашивает чтение новой страницы, а по
предыдущей прочитанной нет ни одного `record_finding` и она не помечена
`mark_irrelevant` — рантайм вставляет синтетическое сообщение:

```
Страница {pageId} прочитана, но результат не зафиксирован.
Вызови record_finding или mark_irrelevant перед следующим чтением.
Текст страницы будет удалён из контекста после этого хода.
```

Не более одного раза подряд. Если модель проигнорировала — вытеснение
выполняется всё равно, `coverage.unrecorded` пополняется `pageId`,
и это попадает в метрики как дефект качества.

### Структура реестра

```
question: string
subQuestions: [{id, text, status: OPEN|ANSWERED|NOT_FOUND|BLOCKED}]
findings:     [{id, subQ, claim, pageId, quote, confidence}]
coverage:     {spaces[], cqlTried[], pagesRead[], pagesSkipped[], unrecorded[]}
```

`coverage` при сжатии реестра урезается **последним**: именно он превращает
`NOT_FOUND` в обоснованный ответ и блокирует повторный поиск.

---

## 5. Бюджет — параметрический

Хардкод абсолютных значений запрещён: окно будет уменьшаться.

```
W            окно из конфига
MAX_OUT      max_tokens, задаётся ЯВНО всегда
CEILING      = 0.80·W − MAX_OUT        // 20 % — запас на ошибку оценщика
F            статический префикс (system + схемы инструментов) — КОНСТАНТА
ALLOC        = CEILING − F − |вопрос|
```

Распределение `ALLOC`:

| Сегмент | Доля | Назначение |
|---|---|---|
| `ledger` | 20 % | render реестра |
| `rawWindow` | 55 % | сырые результаты инструментов |
| `turn` | 15 % | текущее сообщение модели, синтетические вставки |
| `headroom` | 10 % | не расходуется, страховка |

Конкретные значения:

| W | MAX_OUT | CEILING | F | ALLOC | ledger | rawWindow | turn |
|---|---|---|---|---|---|---|---|
| 100k | 8k | 72k | 5k | 66k | 13k | **36k** | 10k |
| 64k | 6k | 45k | 5k | 39k | 8k | **21k** | 6k |
| 32k | 4k | 21.6k | 3k\* | 18k | 3.6k | **10k** | 2.7k |

\* компактный профиль промпта, см. §5.1

Производные:

```
MAX_RESULT_TOKENS = 0.33 · rawWindow      // 12k / 7k / 3.3k — кап на один результат
PROTECTED_RESULTS = 2                     // последние 2 результата не вытесняются
```

### 5.1 Ловушка фиксированного префикса

`F` — константа, а не доля. При `W`=100k это 7 % полезного объёма, при `W`=32k — уже 17 %.

**MUST:** два профиля промпта.

| Профиль | `F` | Когда |
|---|---|---|
| Полный | ~5k | `W ≥ 64k` |
| Компактный | ~3k | `W < 64k` — урезанные описания инструментов, без примеров |

## 6. Preflight

```java
int estimated = estimator.estimate(messages);
if (estimated + MAX_OUT + margin(estimated) > W) {
    degradeInPlace();      // §7, детерминированно, ДО отправки
    estimated = estimator.estimate(messages);
    if (estimated + MAX_OUT + margin(estimated) > W) {
        return error(CONTEXT_OVERFLOW);
    }
}
send(messages, MAX_OUT);
```

* `margin(x) = 0.15·x` — покрывает ошибку эвристического оценщика.
* `MAX_OUT` передаётся в API **явно всегда**. Иначе thinking-режим выест окно
  на генерации, и отказ придёт в середине ответа.
* Реактивный ретрай на ошибку прокси остаётся, но только как страховка от
  промаха оценщика. Каждое срабатывание — в метрики: частые означают,
  что оценщик требует перекалибровки.

---

## 7. Лестница сжатия

Уровни применяются по порядку, следующий — только если предыдущий не помог.

| # | Уровень | LLM | Стоимость | Обратимо |
|---|---|---|---|---|
| 1 | Ingest-кап | нет | O(1) | да, через RawStore |
| 2 | Вытеснение сырых результатов | нет | O(1) | да, через RawStore |
| 3 | Сжатие реестра | нет | O(n) | частично |
| 4 | Аварийная суммаризация | **да** | секунды | нет |
| 5 | Отказ `CONTEXT_OVERFLOW` | — | — | — |

### 7.1 Ingest-кап

Применяется **при записи результата в лог**, один раз.

```
если result.tokens > MAX_RESULT_TOKENS:
    сохранить полный текст в RawStore
    оставить в контексте: голова (60 %) + маркер + хвост (40 %)
```

Маркер:
```
[…усечено N токенов, полный текст доступен по reopen(pageId)…]
```

Хвост сохраняется, потому что в Confluence-страницах итоги, ссылки на смежные
страницы и таблицы часто находятся в конце.

**MUST:** `get_page` вызывается только если `get_section` вернул пусто.
Это самый дорогой инструмент и главный источник переполнения.

### 7.2 Вытеснение

Обход `rawWindow` от конца к началу:

```
protectedSoFar = 0
for result in rawWindow reversed:
    if result.evicted: break
    if protectedSoFar < PROTECTED_RESULTS: protectedSoFar++; continue
    victims += result
```

Вытесненный результат заменяется в проекции на:

```
[ПРОЧИТАНО] {toolName} pageId={id} "{title}" {url}
Зафиксировано находок: {n}. Текст удалён из контекста.
Страница УЖЕ ПРОЧИТАНА — повторный вызов запрещён.
Нужен текст снова — вызови reopen(pageId, focus).
```

**MUST:** факт вызова инструмента сохраняется всегда, удаляется только payload.
Иначе модель решит, что инструмента не вызывала, и вызовет повторно.

`pageId` / `title` / `url` извлекаются один раз при записи, а не при рендеринге.

### 7.3 Сжатие реестра

По порядку, до достижения бюджета:

1. `quote` в findings: обрезка до 120 символов
2. findings по закрытым подвопросам: только `claim`, без `quote`
3. findings с `confidence = LOW`: удаление
4. `coverage.pagesSkipped`: свёртка в счётчик

**MUST:** `coverage.cqlTried`, `coverage.pagesRead` и открытые подвопросы
не удаляются никогда — на них держится защита от повторного поиска.

### 7.4 Аварийная суммаризация

Только если уровни 1–3 не дали результата.

* Отдельный вызов, thinking **выключен**, `temperature = 0`.
* Жёсткий кап вывода: `SUMMARY_MAX = 0.15 · ALLOC`.
* Результат становится границей: следующие ходы получают
  `system + вопрос + summary + сообщения после границы`.
* **MUST:** неудачная суммаризация (ошибка / пустой вывод) **не двигает границу**.
* 3 неудачи подряд → уровень 5.

## 8. Thinking-режим

| Операция | Thinking | Основание |
|---|---|---|
| Основной цикл | **вкл** | планирование, триаж, синтез |
| Аварийная суммаризация | **выкл** | сжатие рассуждения не требует |

Reasoning-токены считаются в окно и непредсказуемы по объёму — отсюда запас
20 % в `CEILING`, а не 10 %.

## 9. Деградация при уменьшении W

Что отключается по мере сжатия окна, в этом порядке:

| # | Отключается | Потеря |
|---|---|---|
| 1 | `get_page` целиком → только `get_section` | низкая |
| 2 | `PROTECTED_RESULTS`: 3 → 2 → 1 | низкая |
| 3 | Длина `quote` в findings | низкая до порога валидации |
| 4 | Число страниц «в полёте»: 4 → 2 → 1 | **высокая — точка перелома** |
| 5 | Многошаговый обход ссылок | высокая для связанных тем |
| 6 | Реестр до `coverage`-only | синтез становится поверхностным |

**Точка перелома — ступень 4.** Ниже двух страниц в контексте одновременно
агент теряет способность сопоставлять источники и вырождается в
последовательный пересказ. Это должно отражаться в `meta.degraded`,
а не маскироваться.

**Граница применимости схемы: `W ≥ 48k`.** Ниже `rawWindow` не вмещает даже
одну среднюю страницу вместе с реестром — переходить на Спецификацию 2.

## 10. Реализация

### 10.1 Оценщик токенов

```java
@Component
public class TokenEstimator {
    private static final double CPT_CYRILLIC = 2.0;
    private static final double CPT_LATIN    = 4.0;

    public int estimate(String text) {
        if (text == null || text.isEmpty()) return 0;
        int probe = Math.min(text.length(), 2000);
        int cyr = 0;
        for (int i = 0; i < probe; i++) {
            char c = text.charAt(i);
            if (c >= 0x0400 && c <= 0x04FF) cyr++;
        }
        double cpt = ((double) cyr / probe) > 0.3 ? CPT_CYRILLIC : CPT_LATIN;
        return (int) Math.ceil(text.length() / cpt);
    }
}
```

Точный токенизатор (jtokkit) — только в тестах калибровки. В горячем пути его нет:
`usage` от прокси может быть недостоверным, а точный подсчёт на каждом ходу
стоит десятки миллисекунд без выигрыша в качестве решения.

### 10.2 Приём результата с ингест-капом

```java
public LogEntry ingest(String tool, String pageId, String raw, BudgetProfile b) {
    int tokens = estimator.estimate(raw);
    rawStore.put(pageId, raw);                       // полный текст — всегда вне контекста

    String contextText = raw;
    boolean truncated = false;
    if (tokens > b.maxResultTokens()) {
        int keep = (int) (raw.length() * ((double) b.maxResultTokens() / tokens));
        int head = (int) (keep * 0.6);
        int tail = keep - head;
        contextText = raw.substring(0, head)
            + "\n[…усечено " + (tokens - b.maxResultTokens())
            + " токенов, полный текст доступен по reopen(" + pageId + ")…]\n"
            + raw.substring(raw.length() - tail);
        truncated = true;
    }
    return LogEntry.toolResult(tool, pageId, contextText, truncated, estimator);
}
```

### 10.3 Пересборка контекста

```java
public List<Message> buildContext(AgentState s, BudgetProfile b) {
    List<Message> ctx = new ArrayList<>();
    ctx.add(s.systemPrompt(b.profile()));            // полный или компактный
    ctx.add(userMessage(s.question()));
    ctx.add(systemMessage(ledgerRenderer.render(s.ledger(), b.ledgerBudget())));

    int used = 0;
    List<Message> raw = new ArrayList<>();
    for (LogEntry e : s.rawWindowNewestFirst()) {    // от свежих к старым
        String rendered = e.renderForModel();        // стаб, если вытеснен
        int t = e.effectiveTokens();
        if (used + t > b.rawWindowBudget()) { e.markEvicted(); rendered = e.renderForModel(); t = e.effectiveTokens(); }
        used += t;
        raw.add(0, toMessage(e.kind(), rendered));
    }
    ctx.addAll(raw);
    ctx.add(s.lastAssistantMessage());
    return ctx;
}
```

Вытеснение выполняется **в момент сборки**, а не отдельным проходом:
бюджет проверяется ровно там, где он расходуется.

## 12. Тесты

1. Контекст на 30-м ходу не превышает контекст на 10-м более чем на 15 % (инвариант 1).
2. Ни один запрос не отправлен без preflight (проверка на моке транспорта).
3. `MAX_OUT` присутствует в каждом запросе.
4. Ingest-кап: результат > `MAX_RESULT_TOKENS` усечён, полный текст в `RawStore`.
5. `reopen(pageId)` возвращает исходный текст побайтово.
6. Вытесненный результат рендерится со стабом, содержащим `pageId` и запрет повтора.
7. Последние `PROTECTED_RESULTS` не вытесняются.
8. Сжатие реестра не удаляет `cqlTried`, `pagesRead` и открытые подвопросы.
9. Неудачная суммаризация не двигает границу.
10. Идемпотентность: повторная сборка контекста без новых событий даёт тот же результат.
11. Калибровка: средняя ошибка оценщика против jtokkit ≤ 20 % на фикстурах реальных страниц.
12. Профили: при `W = 32k` выбран компактный промпт, `F ≤ 3k`.
13. Все бюджеты пересчитываются при `W = 100k / 64k / 48k` без правки кода.

---

## 13. Границы применимости

**Подходит:** узкие и средние запросы, 5–20 страниц, 10–25 ходов, `W ≥ 48k`.

**Не подходит:** широкие исследования на 30+ страниц. Каждая страница занимает
контекст несколько ходов подряд и оплачивается многократно; `rawWindow`
вмещает 3–4 страницы, поэтому сопоставление источников ограничено. Для таких
задач — Спецификация 2.

**Сильная сторона, которой нет у Спецификации 2:** модель видит сырой текст
и может заметить релевантное, что не попало бы ни в один конспект.

# Спецификация 2: управление контекстным окном — оркестратор + reader-субагенты

Область: только context engineering. Guard'ы цикла, grounding-валидация и контракт
ответа описаны в основной спецификации агента и здесь не дублируются.

Условия окружения (`kimi-k2-6`, `W` = 100 000 с возможностью уменьшения, ошибка
прокси на лимите, отсутствие prompt caching, MCP с пятиуровневой очисткой)
идентичны Спецификации 1 — см. её §1–§2. Инварианты 1 и 2 действуют и здесь.

---

## 1. Центральный инвариант

> **Инвариант 3. Сырой текст страницы Confluence никогда не попадает
> в контекст оркестратора. Ни на одном ходу, ни в каком виде.**

Оркестратор оперирует брифами. Чтение — работа reader'а.

Цифры на волне из 8 страниц по 8k:

| Схема | Контекст оркестратора |
|---|---|
| Сырой текст | 8 × 8k + база 22k = **86k** → отказ при потолке 80k |
| Только брифы | 8 × 1k + база 22k = **30k** |

Это не оптимизация — без изоляции схема на восьми страницах просто не работает.

---

## 2. Границу проводит тип данных, а не инструмент

Не всё уходит в reader'ы:

| Данные | Объём | Куда |
|---|---|---|
| Результаты CQL: `pageId`, `title`, `excerpt` | ~50 ток/хит | **в оркестратор** |
| Тело страницы или секции | 3–15k | **только в reader** |

Триаж по заголовкам и выдержкам стоит ~50 токенов на страницу, чтение — 3000–15000.
Один дополнительный проход ранжирования окупается двадцатикратно. Именно здесь
следует тратить и токены, и время.

> **Отбор важнее сжатия. Самый дешёвый токен — незагруженный.**

---

## 3. Фасадные инструменты

**MUST:** инструменты MCP не экспонируются модели. Модель видит фасад
уровня агента, за которым рантайм скрывает и MCP, и reader'ов.

```
search(query, spaces?)            → [{pageId, title, excerpt, score}]
read_pages(pageIds[], focus)      → [{pageId, brief, citations[], status}]
reopen(pageId, focus)             → {pageId, brief, citations[]}
record_finding(...) / close_subquestion(...)
finish(status)
```

* `search` — тонкая проекция `search_cql`, тела не возвращает никогда.
* `read_pages` — композит: параллельные `get_section`/`get_page` → параллельные
  вызовы reader'ов → массив брифов. Сырой текст живёт в Java-переменной
  и там же умирает.
* `reopen` — перечитывание из `RawStore` с другим фокусом, без обращения
  к Confluence.

**Почему фасад, а не перехват `tool_result` и не plan-execute:**

| Вариант | Оценка |
|---|---|
| Plan-execute (модель выдаёт план, без tool-calling) | модель обучена на tool-calling и в режиме генерации плана объективно слабее; валидацию плана придётся строить самому — это переизобретение tool-calling |
| Перехват результата (подмена на расписку) | модель запросила текст, получила расписку — рассинхрон её ожиданий с реальностью, лечится только промптом, то есть ненадёжно |
| **Фасад** | модель работает в нативном режиме; инвариант обеспечен **поверхностью API, а не дисциплиной** — инструмента, возвращающего сырой текст, у неё не существует |

**Цена фасада:** оркестратор не может заметить то, что упустил reader. Компенсации — §6.

---

## 4. Reader — функция сжатия, а не агент

**MUST:** у reader'а нет tool-calling, нет цикла, нет состояния.
Один вызов: текст на входе — бриф на выходе.

Без кэширования системный префикс оплачивается каждым reader'ом на каждом ходу.
При 12 читателях и префиксе 4.5k это 54k токенов за волну ни на что.
Убирая у reader'а инструменты, вы убираете их схемы из префикса.

| | Reader-агент | Reader-функция |
|---|---|---|
| Префикс | ~4.5k | **~600** |
| Вызовов на страницу | 3–5 | **1** |
| Риск зацикливания | есть | **нет** |
| Параллелизм | сложный | тривиальный |

Reader работает с thinking **выключенным**: сжатие текста рассуждения не требует,
а reasoning-токены — основная непредсказуемая статья расхода окна.

### Вход reader'а

**MUST:** reader получает исходный вопрос и открытые подвопросы, а не только keywords.
Это разница между «конспект страницы» и «что на этой странице отвечает на вопрос X».

```
Исходный вопрос исследования: {question}
Открытые подвопросы: {subQuestions}
Фокус текущей волны: {focus}

<untrusted_content source="pageId={id}">
{текст секции или страницы}
</untrusted_content>
```

### Выход reader'а

Structured output, жёсткая схема:

```json
{
  "pageId": "123456",
  "relevance": "HIGH | MEDIUM | NONE",
  "brief": "≤ BRIEF_MAX токенов",
  "citations": [{"quote": "дословно из текста", "subQuestionId": "sq3"}],
  "leads": [{"pageId": "789", "why": "..."}],
  "gaps": "чего на странице нет, хотя ожидалось"
}
```

* `relevance = NONE` → бриф в контекст оркестратора **не попадает вообще**,
  фиксируется только в `coverage.pagesSkipped`. Это основная экономия волны.
* `leads` — ссылки на смежные страницы: топливо для следующей волны.
* `gaps` — то, что не даст оркестратору решить, будто вопрос закрыт.

---

## 5. Волновой цикл

```
Оркестратор (thinking вкл)
  ├─ план: подвопросы, CQL-стратегия
  ├─ search(...) → N хитов, только метаданные
  ├─ триаж: ранжирование, отбор top-K
  ├─ read_pages([K страниц], focus)
  │    └─ рантайм: параллельно MCP → параллельно reader'ы (thinking выкл)
  ├─ брифы → реестр
  └─ решение: следующая волна | reopen | синтез
```

**Волна — единица планирования.** Оркестратор не читает страницы по одной:
он формирует пакет, получает пакет брифов и один раз обновляет картину.
Это сокращает число ходов оркестратора — главный драйвер стоимости без кэша.

```
K_wave        = clamp(briefBudget / BRIEF_MAX / 3, 2, 12)
READER_BATCH  = 1..3 страницы на один вызов reader'а
PARALLELISM   = min(K_wave, лимит одновременных запросов прокси)
```

**MUST:** параллелизм ограничивается пулом с явным лимитом. Корпоративный прокси
почти наверняка имеет квоту одновременных соединений; 12 запросов разом её выберут.

**Отказ одного reader'а не отменяет волну.** Страница помечается
`status = READER_FAILED`, попадает в `coverage`, волна продолжается.
Ретрай — один раз, затем страница уходит в очередь на следующую волну.

---

## 6. Компенсация потерь при сжатии

Reader сжимает страницу, не видя картины исследования целиком. Он не знает,
что нашли соседние reader'ы. Значит бриф — потеря, которую оркестратор
не может обнаружить.

Три компенсации, все обязательны:

1. **Query-aware сжатие** — §4, вход reader'а содержит вопрос и подвопросы.
2. **`RawStore` по ключу `pageId + version`** — сырые тексты хранятся вне контекста
   весь запрос. `reopen(pageId, focus)` перечитывает с другим фокусом: Confluence
   не дёргается, платится только вызов reader'а. **Потеря становится обратимой.**
3. **Поле `gaps` в брифе** — reader обязан сообщить, чего на странице не оказалось.
   Без него оркестратор склонен считать подвопрос закрытым по первому же брифу.

Без пункта 2 единственный способ исправить плохой бриф — полный повторный обход;
на 30-ходовом исследовании это неприемлемо. Закладывать сразу, не откладывать.

---

## 7. Бюджет — параметрический

Два независимых бюджета. Формулы общие с §5 Спецификации 1.

### 7.1 Оркестратор

```
CEILING_O = 0.80·W − MAX_OUT_O        MAX_OUT_O = 8k (thinking вкл)
```

| Сегмент | W=100k | W=64k | W=32k |
|---|---|---|---|
| `F` (фасад: 5 инструментов) | 4k | 4k | 2.5k\* |
| вопрос + план | 1k | 1k | 0.5k |
| `ledger` | 14k | 9k | 5k |
| брифы текущей волны | 12k | 8k | 5k |
| ход | 4k | 3k | 2k |
| **пик** | **35k** | **25k** | **15k** |
| CEILING | 72k | 45k | 21.6k |
| запас | **2×** | 1.8× | 1.4× |

\* компактный профиль промпта

**Оркестратор не использует окно целиком намеренно.** Без кэша каждый токен
оплачивается на каждом ходу; заполнять 72k при работоспособных 35k — прямой убыток.
Установившийся размер держится пересборкой контекста из реестра (инвариант 1).

### 7.2 Reader

```
CEILING_R = 0.80·W − MAX_OUT_R        MAX_OUT_R = 1.5k (thinking выкл)
BRIEF_MAX = clamp(0.035 · briefBudget, 400, 1200)
```

| | W=100k | W=64k | W=32k |
|---|---|---|---|
| CEILING_R | 78.5k | 49.7k | 24.1k |
| префикс | 0.6k | 0.6k | 0.6k |
| страниц в батче | 3 | 2 | **1** |
| `BRIEF_MAX` | 1200 | 900 | 600 |

Reader упирается в окно только на `W < 24k`. Ограничение батча — качество сжатия,
а не размер окна.

---

## 8. Preflight

Действует для **обоих** уровней, механика из §6 Спецификации 1.

Дополнительно для `read_pages`:

```
до отправки в reader:
    est = префикс + вопрос + подвопросы + Σ страниц
    если est + MAX_OUT_R + margin > W:
        уменьшить батч (3 → 2 → 1)
        если не помогло — усечь страницу по ingest-капу, полный текст в RawStore
        если и это не помогло — status = TOO_LARGE, страница в coverage
```

**MUST:** страница, не влезающая в окно reader'а даже одна, обрабатывается
секционно (`get_section` с уточнёнными keywords), а не выбрасывается молча.

---

## 9. Инвариант, проверяемый в коде

```java
// перед каждым вызовом оркестратора
for (Message m : ctx) {
    if (m.tokens() > MAX_ORCHESTRATOR_MESSAGE) {          // 2000
        throw new RawLeakException(m.origin());
    }
}
```

Ни одно сообщение в контексте оркестратора не превышает размера брифа.
Срабатывание — это **дефект реализации**, а не деградация: где-то сырой текст
обошёл фасад. Покрыть тестом, логировать как критическое.

---

## 10. Сжатие контекста оркестратора

Полная лестница из §7 Спецификации 1 здесь не нужна: сырых данных нет,
контекст растёт медленно. Достаточно двух уровней.

1. **Вытеснение брифов закрытых подвопросов.** Бриф заменяется на стаб
   `[бриф pageId={id} свёрнут, N находок в реестре]`. Обратимо: бриф хранится
   в `BriefStore` вне контекста.
2. **Сжатие реестра** — порядок из §7.3 Спецификации 1, с теми же защищёнными полями.

Аварийная LLM-суммаризация в этой схеме — признак ошибки проектирования.
Оставить как последний уровень с алертом в метриках, но при корректных бюджетах
она не должна срабатывать никогда.

---

## 11. Деградация при уменьшении W

| # | Отключается | Потеря |
|---|---|---|
| 1 | `READER_BATCH`: 3 → 2 → 1 | нулевая, растёт число вызовов |
| 2 | `BRIEF_MAX`: 1200 → 600 | низкая до порога валидации цитат |
| 3 | `K_wave`: 12 → 6 → 3 | средняя, компенсируется числом волн |
| 4 | **Число волн: 4 → 2 → 1** | **высокая — точка перелома** |
| 5 | Обход `leads` (многошаговость) | высокая для связанных тем |
| 6 | Реестр до `coverage`-only | синтез становится поверхностным |

Ступени 1–3 почти бесплатны — в этом главное преимущество схемы.
**Ступень 4 — точка перелома:** ниже двух волн агент перестаёт быть
research-агентом и вырождается в обычный RAG-поиск. Это должно попадать
в `meta.degraded`, а не маскироваться.

**Граница применимости: `W ≥ 24k`.** Ниже reader не вмещает страницу целиком,
и всё чтение уходит в посекционный режим с падением качества сжатия.

---

## 12. Реализация

### 12.1 Фасад `read_pages`

```java
public List<Brief> readPages(List<String> pageIds, String focus, ResearchContext ctx) {
    List<List<String>> batches = Lists.partition(pageIds, budget.readerBatch());

    return batches.parallelStream()
        .map(batch -> {
            // сырой текст существует только внутри этого лямбда-выражения
            List<PageText> texts = batch.stream()
                .map(id -> {
                    String raw = mcp.getSection(id, ctx.keywords());
                    if (raw.isBlank()) raw = mcp.getPage(id);
                    rawStore.put(id, raw);                 // для reopen
                    return new PageText(id, raw);
                })
                .toList();

            return reader.compress(texts, ctx.question(), ctx.openSubQuestions(), focus);
        })
        .flatMap(List::stream)
        .filter(b -> b.relevance() != Relevance.NONE)      // NONE в контекст не идёт
        .toList();
    // texts вышли из области видимости — в контекст оркестратора попасть не могут
}
```

Ключевое: `PageText` не является полем класса и не попадает ни в один объект,
достижимый из `AgentState`. Инвариант 3 обеспечен областью видимости переменной.

### 12.2 Reader

```java
public List<Brief> compress(List<PageText> pages, String question,
                            List<SubQuestion> open, String focus) {
    ChatOptions opts = ChatOptions.builder()
        .temperature(0.0)
        .thinking(false)                  // сжатие рассуждения не требует
        .maxTokens(MAX_OUT_R)             // задаётся всегда явно
        .build();

    String prompt = readerTemplate.render(question, open, focus, pages);
    preflight.assertFits(prompt, MAX_OUT_R);              // §8

    return structuredOutput(llm.call(prompt, opts), Brief.LIST_SCHEMA);
}
```

### 12.3 Пересборка контекста оркестратора

Механика идентична §10.3 Спецификации 1, но `rawWindow` заменён на `briefWindow`,
и per-message кап равен `MAX_ORCHESTRATOR_MESSAGE`.

---

## 13. Метрики

К метрикам из §11 Спецификации 1 добавляются:

| Метрика | Что показывает |
|---|---|
| `raw_leak` | срабатывания §9. Цель — строгий ноль |
| `reader.relevance_none_ratio` | качество триажа: высокий = читаем лишнее |
| `reopen_rate` | качество сжатия: высокий = брифы теряют нужное |
| `reader.failed_ratio` | устойчивость параллельного слоя |
| `waves_per_answer` | фактическая глубина исследования |
| `recall@read` | прочитано / релевантно по golden set |

**Кривая `recall@read` против `tokens_per_answer` при `K_wave` = 3 / 6 / 12,
построенная на golden set, даёт рабочую точку.** Она будет своя для вашего
Confluence — универсального значения нет.

## 14. Тесты

1. **Инвариант 3:** после `read_pages` ни одно сообщение контекста оркестратора
   не содержит подстроки из сырого текста страницы.
2. Ни одно сообщение оркестратора не превышает `MAX_ORCHESTRATOR_MESSAGE`.
3. Брифы с `relevance = NONE` отсутствуют в контексте и присутствуют в `coverage`.
4. `reopen(pageId)` не обращается к MCP (проверка на моке).
5. Отказ одного reader'а не прерывает волну; страница помечена `READER_FAILED`.
6. Параллелизм не превышает лимит пула.
7. Preflight reader'а: батч уменьшается до 1 при нехватке окна.
8. Страница, не влезающая одна, обрабатывается посекционно, не выбрасывается.
9. `MAX_OUT` присутствует в каждом запросе обоих уровней.
10. Контекст оркестратора на 30-м ходу не превышает контекст на 10-м более чем на 15 %.
11. Reader вызывается с `thinking = false`, оркестратор — с `true`.
12. Все бюджеты пересчитываются при `W = 100k / 64k / 32k` без правки кода.
13. Reader детерминирован: одинаковый вход даёт одинаковую схему вывода
    (набор `pageId` и `relevance`; текст брифа — нет).

---

## 15. Границы применимости

**Подходит:** широкие исследования, 20–60 страниц, 4+ волны, `W` от 24k до 100k+.
Схема почти не деградирует при сжатии окна — это её главное свойство.

**Не подходит:** запросы на 1–3 страницы. Накладные расходы на волновой цикл
и вызовы reader'ов не окупаются; Спецификация 1 отвечает быстрее и дешевле.

**Слабая сторона:** оркестратор не видит сырого текста и не может заметить
релевантное, не попавшее в бриф. Смягчается `reopen` и полем `gaps`,
но не устраняется полностью.

---

## 16. Выбор между спецификациями

| | Спец. 1 | Спец. 2 |
|---|---|---|
| Страниц за запрос | 5–20 | 20–60 |
| Минимальное `W` | 48k | **24k** |
| Пик контекста при `W`=100k | ~72k | **~35k** |
| Ходов оркестратора | 10–25 | 8–15 (волнами) |
| Компонентов | 1 | 2 + пул + `RawStore` |
| Модель видит сырой текст | **да** | нет |
| Устойчивость к сжатию окна | низкая | **высокая** |
| Сложность реализации | **низкая** | средняя |

Схемы совместимы по состоянию: `ResearchLedger`, `RawStore`, оценщик токенов
и preflight одинаковы. Спецификация 1 реализуется первой, Спецификация 2
надстраивается заменой прямых вызовов MCP на фасад — без переделки состояния.






# MCP-сервер поиска по Confluence — итоговые требования

**Контекст.** Сервер — источник данных для пайплайна генерации семантического слоя DWH StarRocks (аналогично работающему Jira MCP). Сборка — opencode (Superpowers), Python, тот же стек и структура, что у существующих MCP-серверов (Jira/GitLab). Отдельно стоящий Confluence Server/DC. Цель — максимально эффективное использование контекстного окна LLM без потери качества поиска.

**Фундаментальный принцип.** Вместо RAG (векторный индекс) — прямые вызовы Confluence REST API на каждый запрос + многоуровневая пост-обработка ответа. Каждый уровень последовательно уменьшает объём данных, попадающих в контекст LLM. Целевое снижение — 90–97% токенов относительно сырого ответа API.


## 1. Архитектура

- **MUST:** Python, стек и структура существующих MCP-серверов (Jira/GitLab) — не новый паттерн ради Confluence.
- **MUST:** авторизация — существующая схема ротации кредов (Windows User Environment Variables, `os.environ`), без нового secrets-механизма.
- **MUST NOT:** персистентный индекс / векторная БД / эмбеддинги / синхронизирующее хранилище в любом виде. Сервер stateless между запросами.
- **MUST:** формат тела страницы — только `body.storage` (сырой XHTML storage-формата). `body.view` (избыточен, CSS/JS-обёртки), `body.editor` (нестабилен между версиями), `export_view` / `anonymous_export_view` (лишние метаданные / потеря авторства) — не использовать.
- **Обязательные библиотеки:** `lxml` (парсинг Confluence XHTML — единственный надёжный вариант при кастомных тегах `ac:` / `ri:`); `html2text` или `markdownify` (HTML→Markdown); `pydantic` (валидация структуры ответа); опционально `cachetools` (только in-process TTL-кеш).

Три MCP-инструмента: `search`, `get_sections`, `get_page`.

---

## 2. Инструмент `search`

Только предварительная фильтрация через CQL — возвращает метаданные-кандидаты, **не** контент.

- **MUST:** только `/rest/api/search?cql=...` (или `/rest/api/content/search`), не листинг контента с клиентской фильтрацией.
- **MUST:** результат — `title`, `excerpt`, `id`, `space`, `url`. `body.storage` на этом шаге **не** запрашивается.
- **MUST:** лимит по умолчанию небольшой (5–10), настраиваемый параметром вызова.
- **MUST:** все фильтры (`space`, `label`, `type=page`, `ancestor`, `lastmodified`) — внутри CQL, не постфильтрацией.
- **MUST:** `type = "page"` явно в каждом запросе, если не указано иное (иначе в выдачу попадают blogpost/attachment/comment).
- **MUST:** скобки при смешивании `AND`/`OR` в составном запросе — приоритет операторов иначе неочевиден.
- **MUST:** `title ~ "фраза"` пробуется первым (более сильный сигнал релевантности), `text ~` — фолбэк. Альтернативные термины — отдельными `text ~ "term"` через `OR`/`AND`, **не** одной фразой с пробелами (иначе требуется буквальное совпадение порядка слов).
- **MUST:** даты — явным значением `"YYYY-MM-DD"`, посчитанным в коде. **Не** relative-функции `now("-90d")` — не гарантированно поддерживаются на Server/DC.
- **MUST:** URL-кодирование CQL-строки при передаче параметром (кириллица, кавычки, спецсимволы иначе ломают запрос).
- **MUST:** pagination/cursor CQL обрабатывается внутри тула, не перекладывается на агента.
- **SHOULD:** описание параметров тула включает 2–3 примера построения CQL из свободного текста / имени сущности (как в search-туле Jira MCP) — логика построения запроса на уровне сервера, а не в промпте конкретного вызывающего агента.

---

## 3. Пост-обработка контента (общий pipeline для `get_page` и `get_sections`)

Применяется к `body.storage` **одной уже полученной страницы**. Порядок уровней:

### Уровень 1 — JSON-декомпозиция (снятие обёртки API)
Извлекается `body.storage.value`; отбрасываются мета-поля API.
Отбрасываются: `_links`, `_expandable`, `extensions`, `history`, `version.message`, `version.minorEdit`, `metadata.properties`, `restrictions`, `descendants`, `container`, `macroRenderedOutput`, `status` (если не архив).
Сохраняются: `id`, `title`, `type`, `space.key`, `space.name`, `version.number`, `version.createdAt`, `body.storage.value`. `ancestors` — только titles; `children` — только count; `metadata.labels` — только если запрошены явно.

### Уровень 2 — XML/XHTML нормализация
- **MUST:** парсинг реальным парсером (`lxml`), **не** regex/blind strip тегов.
- Нормализация namespace `ac:` / `ri:` → плоские теги; удаление служебных атрибутов (`ac:macro-id`, `ac:schema-version`, `ri:version` и т.п.).
- Удаление layout-обёрток без смысловой нагрузки: `ac:layout`, `ac:layout-section`, `ac:layout-cell`, `ac:inline-comment-marker`.

### Уровень 3 — Структурная фильтрация

**Макросы (macro-aware, не blind strip):**
- `toc`, `children-display` / `children`, `page-properties-report`, `recently-updated` — выбрасываются целиком (нулевая инф. ценность, часто большой объём); при необходимости заменяются коротким маркером (`[Table of Contents]`, `[Children: N pages]`).
- `panel` / `info` / `tip` / `note` / `warning` / `expand` — конвертируются в текстовый маркер с пометкой (`> Note: ...`, `[WARNING: ...]`), а не тихо разворачиваются в plain text.
- `code` / `noformat` — сохраняются как fenced code block.
- Вложения, упоминания пользователей, embedded Jira-макросы, диаграммы (Gliffy/Draw.io) — только ссылка/id/маркер (`[JIRA: KEY-123]`, `[DIAGRAM: see original page]`), без разворачивания в текст.
- `anchor`, чисто декоративные — удаляются.

**Таблицы (ключевой сценарий экономии):**
- **MUST:** заголовочная строка + только строки, совпавшие с ключевыми словами запроса (case-insensitive). При нуле совпадений — preview первых N строк (по умолчанию 3) с маркером `...(X more rows)`.
- **MUST:** обрезка по столбцам для широких таблиц — релевантный столбец + 1–2 соседних, не все.
- **MUST:** корректная обработка `rowspan`/`colspan` в заголовках.
- **SHOULD (контекстно-зависимая фильтрация по типу таблицы):** config-таблица (`Parameter/Value/Default`) → совпадения + строка `Default`; status-таблица → только `FAILED`/`WARNING`; log-таблица → последние N + строки с `ERROR`; reference-таблица → только совпавшие строки.

**Списки (`ul`/`ol`):** если элементов > `max_items` (по умолчанию 5) — оставить голову и хвост, середину заменить на `[...X more items...]` (хвост часто содержит важное).

**Ссылки:** внутренние Confluence → `[→ Title](page:ID)`; внешние → `[→ text](domain)`.

**Изображения:** заменяются описанием — `alt`-текст, иначе `[IMAGE: filename]`; диаграммы → `[DIAGRAM: see original page]`.

### Уровень 4 — Экстракция и сжатие текста
- HTML→Markdown (`html2text`/`markdownify`): без inline-стилей, `body_width=0`, отфильтрованные таблицы → Markdown-таблицы, код → fenced blocks.
- Пост-очистка: схлопывание пустых строк (3+ `\n` → 2), удаление дублирующихся заголовков, снятие лишнего markdown-экранирования, сокращение длинных URL.
- **Дедупликация:** одинаковые блоки (footer, «Related pages», disclaimers, excerpt/include) — по fingerprint (hash содержимого элемента). Fingerprint шаблонного контента пространства считается один раз на выборке страниц пространства в рамках текущего прогона (in-process, не персистентно).
- **Boilerplate:** удаление стандартных фраз (`For more information, see…`, `Last updated:…`, `© YYYY … All rights reserved`, `See also`, `Related pages`) и заголовка, дублирующего `title`.

### Уровень 5 — Сборка ответа (Page Map как формат, вычисляемый на лету)
Итоговый объект: `page_id`, `title`, `space`, `url`, `content_digest` (счётчики секций/таблиц/кода + `estimated_tokens_original` / `estimated_tokens_compressed`), `structure_outline` (уровни и заголовки), `key_blocks` (отфильтрованные таблицы/код/параграфы с `header_path`), `metadata` (version, last_updated, labels если запрошены).

## 4. Инструмент `get_sections` (предпочтительный путь перед `get_page`)

- **MUST:** локальная обработка над уже полученным `body.storage` одной страницы, **не** отдельный вызов API. CQL здесь не участвует — он выбирает страницу, а не часть внутри неё.
- **MUST:** разбиение по `<h1>`–`<h6>`: тело секции — всё до следующего заголовка того же или более высокого уровня; текст собирается рекурсивно по поддереву (вложенные `strong`/`a`/`em` и т.п.), не только прямой текст узла.
- **MUST:** скоринг секций по вхождению ключевых слов запроса; совпадение в заголовке весит существенно больше, чем в теле (например ×3), иначе шумное упоминание в тексте перевесит точный заголовок.
- **MUST:** возвращаются top-K секций, K настраиваемый (по умолчанию 1–2) — не одна и не все.
- **MUST:** к тексту каждой найденной секции применяются те же правила Уровней 2–4 (macro-aware очистка, таблицы, дедупликация, сжатие), а не ко всей странице разом.
- **MUST NOT:** подстановка случайной/первой секции при нулевом скоре у всех — только явное `found: false`.
- **SHOULD:** `get_page` — резервный путь (нет подзаголовков либо секционирование не дало совпадений).

## 5. Инструмент `get_page` (полный текст, резервный)

- **MUST:** отдельный тул по id/ключу; **никогда** не вызывается автоматически внутри `search`.
- **MUST:** `expand=body.storage,version,space` явно — не дефолтный expand (history/ancestors/children и пр. не нужны).
- **MUST:** полный pipeline Уровней 1–5.
- **MUST:** жёсткий cap на объём (символы/токены), обрезка по границе абзаца, не байта.
- **MUST NOT:** тихая обрезка — при truncation явный флаг `truncated: true, omitted_chars: N`.

## 6. Контракт ответа (общий для трёх тулов)

- **MUST:** allowlist полей задаётся при формировании ответа (какие поля класть), а не постфактум удалением лишнего из уже собранного объекта.
- **MUST:** одинаковые имена полей в `search`, `get_sections`, `get_page` — чтобы downstream (компакция/агент) работал единообразно.
- **MUST:** три физически различимых состояния — «ничего не найдено» (`found: false`), «ошибка (auth/сеть/rate-limit)», «результат обрезан» (`truncated: true`). Не одно расплывчатое пустое поле на все случаи: неразличимость этих состояний — то, что в Jira-агенте приводило к отказам и выдумыванию.
- **SHOULD:** отдельные признаки для zero-results / rate-limit / auth-error, чтобы агент осмысленно переформулировал запрос, а не слепо повторил тот же.

## 7. API-оптимизации вызовов

- **MUST:** точечный `expand` — `body.storage,version,space`, никогда полный набор (`body.view,history,ancestors,children,descendants,metadata.*,restrictions`).
- **SHOULD:** предварительная фильтрация через CQL до загрузки тел (`search` возвращает только id-кандидатов; `body.storage` грузится лишь для отобранных).
- **SHOULD:** batch-загрузка метаданных нескольких страниц одним запросом (`?ids=...`) вместо N отдельных.

---

## 8. Верификация (часть сборки, не отдельный шаг)

- **SHOULD:** eval-набор 10–15 реальных запросов с известным ожидаемым результатом (конкретные page id).
- **SHOULD:** eval измеряет не только «нашёл/не нашёл», но и фактический размер ответа в символах/токенах — иначе «максимально эффективно» неизмеримо. Пороги приёмки, например: `search` ≤ N токенов на 10 результатов; `get_sections`/`get_page` ≤ M токенов после очистки на типичную страницу пространства.
- **SHOULD:** для `get_sections` отдельно проверяется, что выбрана **правильная** секция (по заголовку), а не просто непустой ответ — на многосекционной странице это разные вещи.

## 9. Целевые метрики сжатия (ориентир, не гарантия)

| Этап | Действие | Порядок экономии |
|---|---|---|
| Уровень 1 | снятие JSON-обёртки API | ~15% |

Ты — сервис поиска контекста в Jira для пайплайна генерации семантического слоя DWH StarRocks. Твоя единственная функция — по входному запросу найти в Jira релевантные материалы через инструмент поиска и вернуть их. Ты не СУБД, не эксперт по структуре таблиц и не отвечаешь из общих знаний — весь ответ строится только на данных, полученных инструментом.

ИНТЕРПРЕТАЦИЯ ВХОДА
Любой запрос — включая «опиши таблицу X», «для чего нужна Y», «что такое Z» — это команда «найди в Jira упоминания X/Y/Z», а не вопрос к базе данных. Трактуй любую формулировку именно так, без исключений.

ПРАВИЛА (обязательны)
1. На каждый запрос — минимум один вызов инструмента поиска, прежде чем формировать любой ответ. Ответ без вызова инструмента запрещён, включая отказы вида «я не СУБД», «уточните запрос», «не могу помочь».
2. Не отправляй входной текст в поиск как есть. Сначала выдели 2–4 ключевых термина: убери префиксы схемы (dwh., stg., core_...), разбей snake_case/CamelCase на слова, отбрось служебные слова запроса («опиши», «покажи», «что такое»).
3. Если поиск пуст — переформулируй и повтори, не более 3 попыток: 1) точная фраза из ключевых терминов; 2) те же термины через OR по отдельности; 3) очевидные синонимы/сокращения. Останавливайся на первой результативной попытке.
4. Если после 3 попыток результатов нет — прямо сообщи об этом и перечисли опробованные формулировки. Это единственный допустимый вид «пустого» ответа.
5. Никогда не восполняй отсутствие результатов догадкой или общими знаниями о таблице. Явное «не найдено» лучше, чем правдоподобная выдумка.

ФОРМАТ ОТВЕТА
Только поля, которые вернул инструмент (заголовок, дата, ключ тикета, суть комментариев). Ничего сверх данных инструмента.

Пример: «опиши таблицу dwh.core_customer_balance» → термины: customer, balance → поиск «customer balance» → пусто → «customer» OR «balance» → пусто → синонимы «client», «клиентский баланс».

# Промпт-инструкции для генерации чанков (BGE-M3 dense, normalize)

Готовый блок инструкций для вставки в промпт LLM. Покрывает 4 типа: Бизнес-сценарий, Бизнес-метрика, SQL-правило, SQL-пример (TABLE/COLUMNS сюда не входят — предполагается, что они генерируются детерминированно из метаданных).

---

## 0. Сквозные принципы (вставить перед инструкциями по типам)

Эти правила критичны именно из-за выбранной конфигурации эмбеддинга — **чистый dense, без sparse/лексического компонента**. Это значит: ранжирование идёт только по углу между нормализованными векторами, лексическое совпадение слов retrieval не учитывает напрямую. Отсюда следствия:

1. **Источник истины** — только переданные метаданные таблиц и SQL-запрос. Запрещено добавлять бизнес-смысл, который не выводится явно из данных. Если для конкретного типа чанка данных недостаточно — вернуть пустое значение, а не придумывать.

2. **Атомарность** — один чанк = одна самостоятельная смысловая единица, понятная без контекста других чанков. Без анафоры («эта таблица», «данный запрос», «он») — называть сущности явно каждый раз.

3. **Дублирование терминологии** — при первом упоминании сущности указывать одновременно бизнес-термин и технический идентификатор: «клиент (CLIENT_ID)», «дата операции (OPER_DT)». Это компенсирует отсутствие лексического поиска: какой бы термин ни использовал пользователь в запросе, он должен присутствовать в тексте чанка.

4. **Однотемность вектора** — нормализованный dense-эмбеддинг даёт один «средний» смысловой вектор на весь текст. Не смешивать в одном чанке несколько несвязанных фактов — это размывает вектор и портит retrieval. Целевая длина: ~60–180 слов (100–300 токенов).

5. **Якорное первое предложение** — должно полностью называть, о чём чанк (сущность/метрика/правило), без вводных фраз и местоимений в начале.

6. **Естественный язык, а не SQL-пересказ** — в чанках Бизнес-сценарий и Бизнес-метрика запрещено цитировать сырой SQL-синтаксис. Условия из WHERE/JOIN должны быть переформулированы как бизнес-смысл. SQL-синтаксис допустим только в SQL-правило и SQL-пример.

7. **Bridge-блок «Типичные вопросы»** (опционально, но рекомендуется) — в конец каждого чанка добавлять 2–3 короткие переформулировки в стиле вопроса пользователя, которые логически привели бы к этому чанку. Это снижает разрыв между лексикой пользовательского NL-запроса и лексикой технического чанка.
   - *Trade-off*: это слегка «размывает» тематическую чистоту вектора. Если для вас важнее чистота темы (например, для последующего re-ranking), храните эти вопросы отдельным полем, не включая в текст, который векторизуется.

---

## 1. Бизнес-сценарий (BUSINESS-SCENARIO)

**Цель:** ответить на вопрос «какую бизнес-задачу решает этот запрос» — кто, зачем, в каком разрезе.

Обязательно включить:
- Бизнес-домен (из метаданных таблиц)
- Центральная бизнес-сущность анализа и разрез/группировка (из GROUP BY запроса)
- Бизнес-условие отбора, переформулированное из WHERE (не как SQL, а как смысл: «только активные клиенты», «за последний завершённый месяц»)
- Предполагаемая цель/потребитель — **только если** очевидно выводится из домена и гранулярности; иначе обобщённо («аналитик домена X»)

Запрещено:
- Построчный пересказ SQL
- Использовать имена таблиц/колонок как единственное описание сущности без расшифровки в бизнес-термины

Шаблон:
> «[Домен] отчёт/анализ по [сущность] в разрезе [измерение]. Отбираются записи с условием: [бизнес-условие]. Используется для [цель, если выводима]. Источники: [таблицы бизнес-именами].»

---

## 2. Бизнес-метрика (METRIC)

**Цель:** «паспорт» метрики — что считается, как, на каком уровне, в каких единицах.

Обязательно включить:
- Название метрики и способ агрегации словами (а не формулой SQL): сумма/количество/доля/среднее
- Гранулярность результата (уровень, на котором считается: клиент/день/продукт — из GROUP BY)
- Единица измерения, **только если** однозначно определяется (рубли, штуки, %); если неочевидно — не указывать
- Бизнес-условия, влияющие на значение метрики (фильтры, меняющие её смысл, напр. «только по активным картам»)

Запрещено:
- Путать с SQL-правилом: метрика — про ЧТО и ПОЧЕМУ считается, не про детали реализации JOIN
- Дублировать формулу как код — только словами

Шаблон:
> «[Название метрики] — это [что измеряет], рассчитывается как [агрегатное действие] по [сущность], в разрезе [гранулярность]. Учитываются только записи, удовлетворяющие условию: [бизнес-условие].»

---

## 3. SQL-правило (SQL-RULE)

**Цель:** зафиксировать неочевидную логику, кодирующую бизнес-правило — то, что не угадать по одним названиям колонок.

Обязательно включить:
- Конкретный фрагмент запроса (JOIN-условие, CASE WHEN, специфичный фильтр), процитированный технически — здесь SQL-синтаксис уместен
- Явное объяснение, какое бизнес-правило это условие реализует
- Если в запросе несколько таких правил — **отдельный чанк на каждое**, не смешивать

Запрещено:
- Описывать тривиальные части (простой SELECT нужных колонок — не правило)
- Пытаться объяснить весь запрос целиком в одном чанке

Шаблон:
> «Правило [название]: используется условие `[SQL-фрагмент]`, что реализует бизнес-логику: [объяснение]. Применяется при определении/расчёте [сущность/метрика].»

---

## 4. SQL-пример (SQL-EXAMPLE)

**Цель:** пара «вопрос → SQL» как образец паттерна для text2sql-генерации.

Обязательно включить:
- Вопрос, сформулированный так, как реальный конечный пользователь спросил бы (не как технический пересказ SQL слово в слово)
- Сам SQL-запрос (нормализованный, без лишнего форматирования, логика сохранена)
- Короткая аннотация паттерна (1 фраза, напр. «паттерн: агрегация с фильтром по статусу + join справочника»)

Запрещено:
- Вопрос — буквальный перевод SQL-конструкций на русский («выбрать сумму, где статус равен...»)

Шаблон:
> «Вопрос: [естественная формулировка]. SQL: [запрос]. Паттерн: [категоризация].»

---

## 5. Рекомендуемый формат вывода LLM

Чтобы упростить парсинг и явно разрешить пустые поля:

```json
{
  "business_scenario": "string | null",
  "metric": "string | null",
  "sql_rule": ["string", "..."],
  "sql_example": "string | null"
}
```

В промпте явно укажите: *«Если для какого-то поля в предоставленных данных недостаточно информации — верни null (или пустой массив для sql_rule), не генерируй предположительный контент»*. Это прямая защита от галлюцинаций при калибровке через повторный LLM-синтез.

# Промпт-инструкции для генерации чанков семантического слоя (v2)

Актуальная архитектура: 1 инструмент семантического поиска (покрывает SQL-RULES / SQL-EXAMPLE / BUSINESS-SCENARIO / METRIC; TABLE-чанки отложены), плюс 2 детерминированных тулза без эмбеддингов — COLUMNS и JOIN (прямой SELECT). У каждого чанка есть `chunk_type` как metadata-поле (фильтрация) и `extra_json` (доп. данные, не участвующие в эмбеддинге).

---

## 0. Решённые архитектурные вопросы (сводка)

- **Тип чанка передаётся через параметр инструмента**, не через текст. Таксономия типов остаётся в описании MCP-тулза (агенту нужно знать, когда переключать `chunk_type`), но это не загрязняет ни эмбеддинг чанка, ни эмбеддинг запроса агента.
- **Никаких тегов/префиксов типа в тексте чанка.** Решение, принятое изначально, подтверждается: тег — низкоинформативный токен, который размывает внутритиповую дифференциацию (одинаковый тег у всех SQL-примеров не помогает отличить их друг от друга, а вектор смещает).
- **Код и точные машинные артефакты не входят в эмбеддируемый текст** — уходят в `extra_json`. Это уже сделано для SQL-EXAMPLE (SQL-код в extra_json), и по той же логике применяется к SQL-RULE.
- **Идентификаторы (имена колонок/таблиц) — не код, остаются в тексте.** `CLIENT_ID`, `REVENUE` — это не синтаксис, а именование сущности, и по принципу дублирования терминологии (см. ниже) должны быть в тексте рядом с бизнес-термином.

---

## 1. Контракт: текст эмбеддинга vs extra_json

Чёткая граница для LLM-генератора чанков:

| Идёт в `text` (эмбеддится) | Идёт в `extra_json` (НЕ эмбеддится) |
|---|---|
| Естественно-языковое описание сущности/правила/метрики/примера | Точный SQL-фрагмент или весь SQL-запрос |
| Имена колонок/таблиц как идентификаторы рядом с бизнес-термином | Список source_tables / columns в структурированном виде (для программного использования) |
| Бизнес-условия, переформулированные словами | Литералы из WHERE, которые не несут смысловой нагрузки в прозе (точные пороги можно оставить в тексте, если они значимы для смысла — напр. «90 дней») |
| Билингвальные названия техник (rolling average / скользящее среднее) | semantic_key / query_type / fingerprint (если есть из вашего sqlglot-пайплайна — переиспользовать готовые поля, не генерировать заново) |

Правило для LLM в промпте: *«Если для объяснения смысла требуется привести точный код — перефразируй код в естественный язык в `text`, а точный код продублируй отдельно в `extra_json.sql_fragment`. Никогда не вставляй SQL-синтаксис (CASE WHEN, JOIN ON, скобки логических выражений) в `text`.»*

---

## 2. Маршрутизация типа чанка — через параметр инструмента

Пример схемы (если ещё не вынесено явно):

```
search_semantic(
  query: str,                 # чистый семантический запрос, без слов "пример"/"метрика"/"правило"
  chunk_type: Literal["business_scenario", "metric", "sql_rule", "sql_example"] | None = None,
  domain: str | None = None   # опционально, если у вас есть доменная фильтрация
)
```

В описании параметра `chunk_type` — явно прописать таксономию для агента, в т.ч. синонимы-триггеры («пример», «как реализовано», «паттерн» → sql_example; «как считается», «формула» → metric). Это переносит ответственность за словарь типов из эмбеддинга в schema-уровень, где он ничего не размывает.

---

## 3. Сквозные принципы текста

1. **Источник истины** — только переданные метаданные таблиц и SQL-запрос. Если данных недостаточно для конкретного типа — вернуть null, не выдумывать.
2. **Атомарность** — один чанк = одна самостоятельная смысловая единица, без анафоры («эта таблица», «он»). Называть сущности явно.
3. **Дублирование терминологии** — бизнес-термин + технический идентификатор при первом упоминании: «клиент (CLIENT_ID)». Критично при чистом dense без sparse-компонента.
4. **Однотемность вектора** — целевая длина text: ~60–180 слов. Не смешивать несколько фактов в одном чанке.
5. **Якорное первое предложение** — сразу называет, о чём чанк, без вводных конструкций.
6. **Билингвальные пары для техник** — для любой вычислительной техники (оконные функции, скользящее среднее, ранжирование, pivot, дедупликация) — пара «русский термин (английский термин)» хотя бы раз в тексте.
7. **Техника вперёд домена** — если SQL-правило/пример реализует универсальную технику, начинать text с самой техники, потом — с домена-приложения. Это сохраняет релевантность и для доменно-нейтральных запросов («rolling average SQL пример»), и для доменных.

---

## 4. Бизнес-сценарий (business_scenario)

**text:** какую бизнес-задачу решает запрос — домен, сущность, разрез, бизнес-условие отбора (переформулированное из WHERE), явные измерения с привязкой к идентификатору («в разрезе категории товара (CATEGORY_ID)»).
**extra_json:** `{"domain": "...", "source_tables": [...], "dimensions": ["CATEGORY_ID", ...]}`

Запрещено: построчный пересказ SQL; голые имена таблиц/колонок без бизнес-расшифровки.

---

## 5. Бизнес-метрика (metric)

**text:** что измеряет метрика, способ агрегации словами, гранулярность результата, единица измерения (только если однозначна), бизнес-условия, влияющие на значение.
**extra_json:** `{"granularity_columns": [...], "source_tables": [...], "formula_hint": "SUM(...)"}` — точную формулу как код держать только в extra_json, если она нужна машинно.

Запрещено: путать с SQL-правилом (метрика — про ЧТО и ПОЧЕМУ, не про детали JOIN); код формулы в text.

---

## 6. SQL-правило (sql_rule)

**text:** естественно-языковое объяснение неочевидной логики без синтаксиса кода. Пример:
> «Активным клиентом считается тот, у кого дата последней операции (LAST_OPER_DT) не более 90 дней до текущей даты, и статус счёта (ACCOUNT_STATUS) равен значению "активный". Это правило применяется при расчёте [метрика/сущность].»

**extra_json:** `{"sql_fragment": "CASE WHEN account_status = 'ACTIVE' AND datediff(current_date, last_oper_dt) <= 90 THEN 1 ELSE 0 END", "source_tables": [...], "columns": [...]}`

Если в запросе несколько правил — отдельный чанк на каждое, не смешивать.

---

## 7. SQL-пример (sql_example)

**text:** естественный вопрос, который реализует запрос (как сформулировал бы конечный пользователь) + краткая аннотация паттерна, бизнес-нейтрально вперёд, если паттерн универсален:
> «Скользящее среднее (rolling average) за 7 дней — паттерн сглаживания временного ряда через оконную функцию. Пример применения: выручка (REVENUE) по категориям товара (CATEGORY_ID) в домене Магазин.»

**extra_json:** `{"sql_query": "...", "source_tables": [...], "semantic_key": "...", "query_type": "..."}` — последние два поля переиспользовать из вашего sqlglot-пайплайна (структурный фингерпринт/семантический ключ), а не генерировать заново через LLM.

Запрещено: вопрос как буквальный перевод SQL; SQL-синтаксис в text.

---
8. Bridge-блок (синтетические варианты запроса)
В text (или отдельным невекторизуемым полем, если важна тематическая чистота) — 2–3 переформулировки, учитывающие что реальный клиент поиска — ассистент, декомпозирующий вопрос:
	•	Естественная: «Как считается средняя выручка за неделю по категориям?»
	•	Кластерная (имитация под-запроса ассистента): «[домен] [сущность] [метрика]» / «[техника RU] [техника EN] [применение]» — без слов «пример»/«метрика»/«правило»/«сценарий»: это покрыто параметром chunk_type, дублировать в text не нужно.
Конкретный пример (sql_example для скользящего среднего выручки по категориям в Магазине):
«Магазин выручка категория товара скользящее среднее 7 дней rolling average»
Соответствующий вызов тулза агентом: search_semantic(query="скользящее среднее 7 дней rolling average выручка категория", chunk_type="sql_example") — type-слово ушло в параметр, в query его нет.

ответ:

# Правила генерации текстов RAG-чанков (embedding_text)

Документ предназначен для использования как набор инструкций в промпте LLM, генерирующей `embedding_text` для каждого типа чанка: TABLE, COLUMNS, SQL-RULES, METRIC, BUSINESS-SCENARIO, SQL-EXAMPLE.

Цель правил — обеспечить симметрию между текстом чанка и трансформированным (нормализованным/декомпозированным) запросом пользователя на этапе семантического поиска, минимизировать шум для cosine similarity и сохранить различимость чанков внутри одного типа.

---

## 0. Универсальные правила (применяются к каждому типу)

**U1. Якорное открытие.**
Первое предложение = название сущности + прямое определение/функция. Без вводных рамочных конструкций ("Эта таблица содержит...", "Данная метрика отвечает за..."). Канонический термин должен находиться в первых 5–8 словах текста.

**U2. Запрет общих шаблонных фраз.**
Не использовать типовые рамочные обороты, повторяющиеся в большинстве чанков одного типа. Такие фразы создают общий смещающий вектор, который искусственно сближает все чанки типа между собой и снижает различимость при retrieval.

**U3. Терминологическая стабильность (контролируемый словарь).**
Для каждого бизнес-понятия фиксируется одна каноническая словоформа, используемая во всех чанках без изменений (например: всегда "выручка", не подменять на "доход" внутри описания). Внутри одного чанка избегать множественных падежных форм одного ключевого термина без грамматической необходимости — предпочтение номинативным конструкциям над глагольно-падежными цепочками. Это снижает шум для морфологической нормализации (pymorphy3) на стороне query understanding и повышает точность лексического совпадения в sparse-компоненте эмбеддинга.

**U4. Самодостаточность (no dangling context).**
Каждый чанк должен быть интерпретируем без соседних чанков:
- явно называть родительский домен/таблицу/бизнес-сценарий внутри текста, а не только в метаданных;
- не использовать анафорические ссылки без антецедента в этом же тексте ("она", "это", "данный показатель" без явного предшествующего упоминания);
- при пересечении с похожей сущностью — явно дизамбигуировать ("не путать с X").

**U5. Разделение embedding-текста и payload.**
Точные идентификаторы (имена колонок, SQL-выражения, технические типы) не растворяются в описательном тексте как основной материал — присутствуют один раз как точный якорь (для гибридного dense+sparse поиска), но не подменяют естественноязычное описание.

**U6. Калибровка длины.**
Целевой бюджет длины фиксируется per-type (см. ниже) и должен быть устойчив внутри типа — отклонение более ±30% от целевой длины нежелательно, чтобы не смещать top-k в сторону более "плотных" чанков.

**U7. Якорные вопросы.**
1–2 примера вопросов на естественном языке, которые закрывает чанк, формулируются как отдельное явно выделенное предложение/поле, не превышающее 20–25% от общего объёма текста чанка.

## 1. Правила по типам чанков

### TABLE
| Параметр | Значение |
|---|---|
| Voice | технически-деловой, function-first ("Таблица фиксирует факт оплаты по договору...") |
| Обязательные элементы | домен, грануляция строки ("одна строка = один платёж"), частота обновления, если релевантно |
| Синонимы/аббревиатуры | **Обязательно.** Таблицы часто известны под разными бытовыми названиями ("клиенты"/"контрагенты"/customers) — указывать как отдельное явное поле/предложение |
| Длина | ~80–150 слов |
| Самодостаточность | обязательно указывать домен (банкинг/маркетплейс/платежи/госуслуги), т.к. похожие имена таблиц встречаются в разных доменах |

### COLUMNS
| Параметр | Значение |
|---|---|
| Voice | точный, телеграфный; бизнес-смысл + формула/единица измерения, если применимо |
| Обязательные элементы | бизнес-смысл (не только тип данных), диапазон/домен значений для категориальных колонок, имя родительской таблицы |
| Синонимы/аббревиатуры | **Обязательно.** В банковско-государственном домене высокая плотность аббревиатур (ИНН, КПП, БИК, СНИЛС) и бытовых синонимов ("сумма"/"amount"/"величина") |
| Длина | ~40–80 слов |
| Самодостаточность | обязательно повторять имя родительской таблицы и домен — общие имена колонок ("amount", "status") повторяются в десятках таблиц |

### SQL-RULES
| Параметр | Значение |
|---|---|
| Voice | нормативный, условный ("Учитывается только..., если...") |
| Обязательные элементы | условие + область применения + краткое бизнес-обоснование |
| Синонимы/аббревиатуры | **Опционально.** Текст про логику, а не про вариативность называния — нужно только если правило ссылается на термин, не закреплённый в другом чанке |
| Длина | ~50–100 слов |
| Самодостаточность | обязательно называть метрику/таблицу/сценарий, к которому правило относится — само правило без субъекта не интерпретируемо |

### METRIC
| Параметр | Значение |
|---|---|
| Voice | дефинитивный + формульный: сначала бизнес-определение, затем формула |
| Обязательные элементы | бизнес-определение, формула/способ агрегации, единица измерения, домен/владелец |
| Синонимы/аббревиатуры | **Обязательно, наивысший приоритет.** Метрики чаще всего переименовываются пользователями ("выручка"/"доход"/"оборот"/revenue), плюс отраслевые аббревиатуры (ARPU, LTV, GMV — если применимо) |
| Длина | ~60–120 слов |
| Самодостаточность | условия фильтрации должны быть встроены прямо в определение, а не вынесены целиком в связанный SQL-RULES чанк |

### BUSINESS-SCENARIO
| Параметр | Значение |
|---|---|
| Voice | компактно-нарративный, use-case фрейминг ("Сценарий описывает процесс начисления кэшбэка при оплате через СБП...") |
| Обязательные элементы | триггер/условие сценария, участвующие роли/сущности, явные ссылки на связанные метрики/таблицы по имени |
| Синонимы/аббревиатуры | **Обязательно.** Корпоративный жаргон и аббревиатуры (СБП, ЕСИА и т.п.) должны быть покрыты — это самый "разговорный" тип чанка |
| Длина | ~100–180 слов (самый насыщенный контекстом тип) |
| Самодостаточность | явно называть пересекающиеся домены (банкинг/маркетплейс/платежи/госуслуги), т.к. сценарии часто кросс-доменные |

### SQL-EXAMPLE
| Параметр | Значение |
|---|---|
| Voice | пара "вопрос + паттерн", минимум нарратива ("Вопрос: ... / Паттерн: JOIN + оконная функция для расчёта...") |
| Обязательные элементы | явная естественноязычная формулировка вопроса (это и есть якорь), тег типа запроса в метаданных (SIMPLE/AGG/WINDOW/JOIN/CTE) |
| Синонимы/аббревиатуры | **Не требуется отдельным полем.** Покрытие вариативности достигается через несколько формулировок вопроса для одного паттерна, а не через список синонимов |
| Длина | вопрос ~15–25 слов + краткое описание паттерна ~30–50 слов; сам SQL — в payload, не в эмбеддируемом тексте |
| Самодостаточность | обязательно называть таблицы/метрики, над которыми построен пример |

## 2. Тег типа чанка в embedding-тексте — решение

**Не включать.**

Обоснование:
1. Токены-теги ("TABLE:", "МЕТРИКА:") повторяются во всех чанках одного типа → создают общий смещающий вектор, который сближает чанки одного типа между собой сильнее, чем по реальному содержанию → снижает discriminative power cosine similarity внутри типа.
2. Тип уже определяется структурно — отдельные retrieval-tools (`search_schema` / `search_business_context` / `search_sql_knowledge`) и/или раздельные векторные неймспейсы решают маршрутизацию на уровне retrieval routing/pre-filter, а не на уровне текста.
3. Query transformation, даже классифицируя intent по типу сущности, не вставляет литерал типа в переформулированный запрос — текстового соответствия не требуется.

Куда вместо этого: `chunk_type` как структурное поле метаданных (для фильтрации/маршрутизации/бустинга), не примешиваемое к dense-эмбеддингу. При использовании гибридного dense+sparse поиска (BGE-M3) тег может существовать как отдельное фильтруемое лексическое поле — но не внутри основного описательного текста.

Универсальные правила стилистики для всех типов чанков
Самодостаточность: каждый чанк должен быть автономным, без ссылок на внешний контекст (“см. выше”, “как указано ранее”).
Минимальная вариативность: избегать лишних словоформ и синонимической избыточности, использовать устойчивые формулировки
Тег типа: включать в начало текста явный тег типа (TABLE:, COLUMNS:, SQL-RULES:, METRIC:, BUSINESS-SCENARIO:, SQL-EXAMPLE:). Это повышает точность семантического поиска и снижает риск смешивания разных классов чанков
Синонимы и аббревиатуры: включать только там, где это критично для поиска (см. ниже).
Синонимы и аббревиатуры включать только в COLUMNS, METRIC, BUSINESS-SCENARIO.
Форматирование: использовать короткие, чёткие предложения; избегать длинных описательных абзацев
Единый стиль: формулировать в стиле “справочник” или “техническая документация”, без художественных элементов.

Итоговые правила для LLM

1. Каждый чанк самодостаточен.
2. Каждый чанк начинается с Тип объекта.
3. Используется канонический термин для каждой сущности.
4. Синонимы выносятся в отдельный блок Синонимы.
5. Аббревиатуры выносятся в отдельный блок Аббревиатуры.
6. TABLE, COLUMN, METRIC, BUSINESS-SCENARIO и SQL-RULE обязательно содержат синонимы и реальные бизнес-аббревиатуры.
7. SQL-EXAMPLE содержит только задачу и реалистичный SQL.
8. Избегаются местоимения и ссылки на соседние чанки.
9. Используются короткие декларативные предложения.
10. Названия таблиц, колонок, метрик и правил всегда указываются явно и полностью.
11. Не использовать избыточную словоформенную вариативность; один основной термин + список синонимов.
12. Все определения формулируются так, как будто чанк будет найден и прочитан отдельно от остальных документов. Это особенно важно для cosine similarity поиска в BGE-M3.


Универсальные правила стиля (для всех 6 типов)

	1.	Двухслойная структура текста: 1) связный абзац на естественном русском, описывающий смысл сущности так, как мог бы сформулировать вопрос пользователь; 2) короткий терминологический блок в конце (“Термины: …”) с каноничными формами синонимов/аббревиатур/технических идентификаторов через запятую.
	2.	Самодостаточность (no dangling context): чанк не должен требовать соседних чанков для понимания. Любая ссылка типа “см. выше”, “эта таблица”, “указанная метрика” — запрещена. Все сущности называются явно и полностью при каждом упоминании (имя таблицы, схема, родительская сущность для колонки и т.д.), даже если это кажется избыточным дублированием между чанками одной группы.
	3.	Каноничная словоформа: одно понятие — одна грамматическая форма (именительный падеж для существительных, инфинитив для глаголов). Не порождать ряд падежных/числовых вариаций одного слова “для покрытия похожих запросов” — dense-модель и так устойчива к морфологии, а ваш query-pipeline лемматизирует запрос на входе. Падежные вариации не добавляют семантического сигнала, только растягивают вектор и съедают токен-бюджет, который лучше отдать настоящим синонимам.
	4.	Лексическое разнообразие — только за счёт настоящих синонимов, не словоформ: “клиент / контрагент / покупатель”, а не “клиент / клиента / клиентом”.
	5.	Нейтрально-декларативный стиль: 3-е лицо, настоящее время, без маркетинговых формулировок (“важная таблица”, “удобная метрика”), без риторических вопросов.
	6.	Бизнес-термин впереди технического идентификатора: “Сумма транзакции (amount, поле amt)”, а не наоборот — пользователь думает бизнес-языком, а не названиями колонок.
	7.	Единая длина/плотность в рамках одного типа чанка — иначе разные по объёму чанки одного типа будут иметь систематически разную “массу” вектора, и более длинные/многословные начнут перетягивать similarity не за счёт релевантности, а за счёт объёма.
