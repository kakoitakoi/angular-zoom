# Промпт-инструкции для генерации чанков семантического слоя (v2)

Актуальная архитектура: 1 инструмент семантического поиска (покрывает TABLE / SQL-RULES / SQL-EXAMPLE / BUSINESS-SCENARIO / METRIC), плюс 2 детерминированных тулза без эмбеддингов — COLUMNS и JOIN (прямой SELECT). У каждого чанка есть `chunk_type` как metadata-поле (фильтрация) и `extra_json` (доп. данные, не участвующие в эмбеддинге). TABLE отличается от остальных 4 типов источником: генерируется не из SQL-запроса, а из метаданных таблицы (имя, схема, домен, цель, гранулярность, колонки, пример данных), один чанк на одну таблицу.

---

## 0. Решённые архитектурные вопросы (сводка)

- **Тип чанка передаётся через параметр инструмента**, не через текст. Таксономия типов остаётся в описании MCP-тулза (агенту нужно знать, когда переключать `chunk_type`), но это не загрязняет ни эмбеддинг чанка, ни эмбеддинг запроса агента.
- **Никаких тегов/префиксов типа в тексте чанка.** Решение, принятое изначально, подтверждается: тег — низкоинформативный токен, который размывает внутритиповую дифференциацию (одинаковый тег у всех SQL-примеров не помогает отличить их друг от друга, а вектор смещает).
- **Код и точные машинные артефакты не входят в эмбеддируемый текст** — уходят в `extra_json`. Это уже сделано для SQL-EXAMPLE (SQL-код в extra_json), и по той же логике применяется к SQL-RULE.
- **Идентификаторы (имена колонок/таблиц) — не код, остаются в тексте.** `CLIENT_ID`, `REVENUE` — это не синтаксис, а именование сущности, и по принципу дублирования терминологии (см. ниже) должны быть в тексте рядом с бизнес-термином.

---

## 1. Контракт: текст эмбеддинга vs extra_json

Чёткая граница для LLM-генератора чанков:

| Идёт в `text` (эмбеддится) | Идёт в `extra_json` (НЕ эмбеддится) |
|---|---|
| Естественно-языковое описание сущности/правила/метрики/примера | Точный SQL-фрагмент или весь SQL-запрос |
| Имена колонок/таблиц как идентификаторы рядом с бизнес-термином | Список source_tables / columns в структурированном виде (для программного использования) |
| Бизнес-условия, переформулированные словами | Литералы из WHERE, которые не несут смысловой нагрузки в прозе (точные пороги можно оставить в тексте, если они значимы для смысла — напр. «90 дней») |
| Билингвальные названия техник (rolling average / скользящее среднее) | semantic_key / query_type / fingerprint (если есть из вашего sqlglot-пайплайна — переиспользовать готовые поля, не генерировать заново) |

Правило для LLM в промпте: *«Если для объяснения смысла требуется привести точный код — перефразируй код в естественный язык в `text`, а точный код продублируй отдельно в `extra_json.sql_fragment`. Никогда не вставляй SQL-синтаксис (CASE WHEN, JOIN ON, скобки логических выражений) в `text`.»*

---

## 2. Маршрутизация типа чанка — через параметр инструмента

Пример схемы (если ещё не вынесено явно):

```
search_semantic(
  query: str,                 # чистый семантический запрос, без слов "пример"/"метрика"/"правило"
  chunk_type: Literal["table", "business_scenario", "metric", "sql_rule", "sql_example"] | None = None,
  domain: str | None = None   # опционально, если у вас есть доменная фильтрация
)
```

В описании параметра `chunk_type` — явно прописать таксономию для агента, в т.ч. синонимы-триггеры («пример», «как реализовано», «паттерн» → sql_example; «как считается», «формула» → metric). Это переносит ответственность за словарь типов из эмбеддинга в schema-уровень, где он ничего не размывает.

---

## 3. Сквозные принципы текста

1. **Источник истины** — только переданные метаданные таблиц и SQL-запрос. Если данных недостаточно для конкретного типа — вернуть null, не выдумывать.
2. **Атомарность** — один чанк = одна самостоятельная смысловая единица, без анафоры («эта таблица», «он»). Называть сущности явно.
3. **Дублирование терминологии** — бизнес-термин + технический идентификатор при первом упоминании: «клиент (CLIENT_ID)». Критично при чистом dense без sparse-компонента.
4. **Однотемность вектора** — целевая длина text: ~60–180 слов. Не смешивать несколько фактов в одном чанке.
5. **Якорное первое предложение** — сразу называет, о чём чанк, без вводных конструкций.
6. **Билингвальные пары для техник** — для любой вычислительной техники (оконные функции, скользящее среднее, ранжирование, pivot, дедупликация) — пара «русский термин (английский термин)» хотя бы раз в тексте.
7. **Техника вперёд домена** — если SQL-правило/пример реализует универсальную технику, начинать text с самой техники, потом — с домена-приложения. Это сохраняет релевантность и для доменно-нейтральных запросов («rolling average SQL пример»), и для доменных.

---

## 4. TABLE (паспорт таблицы)

**Отличие от остальных 4 типов:** генерируется не из SQL-запроса, а из метаданных таблицы целиком — один чанк на одну таблицу. Используется для верхнего уровня иерархии (Domain Router → Table Passport → ...) — найти подходящую таблицу(и) среди множества таблиц DWH. Приоритет здесь — не «ответить на вопрос», а **различимость среди похожих/соседних таблиц**: при сотнях таблиц на 4 домена (банк/маркетплейс/платежи/госуслуги) ошибка выбора таблицы на этом уровне дороже, чем ошибка на уровне отдельной метрики — она ломает весь дальнейший pipeline.

**Обязательно включить в text:**
1. Домен + бизнес-сущность + технический идентификатор (схема.таблица) — в анкерном предложении.
2. **Гранулярность явно и в начале** («одна строка = ...») — самый частый источник путаницы между похожими таблицами (детальная таблица vs агрегат, снапшот vs история).
3. Назначение — переформулировка поля «цель таблицы» в естественный язык.
4. **Синонимы/сокращения — обязательно** (для TABLE это не опция, в отличие от остальных типов): технические имена таблиц часто кодовые/нечитаемые (`DWH_CLN_TRX_DTL`), бизнес-пользователи и агенты называют сущность иначе. Перечислить альтернативные названия по доменам.
5. **Граница охвата** — что НЕ входит / чем отличается от соседних таблиц: retention-период, фильтр по статусу при загрузке, источник, «это не агрегат» и т.п. Самый сильный инструмент дифференциации среди похожих сущностей — добавлять, если такая похожая таблица есть.

**extra_json:** `{"schema": "...", "table_name": "...", "domain": "...", "grain": "..."}` — точные идентификаторы для последующего вызова COLUMNS/JOIN по этой таблице.

Шаблон:
> «[Домен] таблица [бизнес-сущность] (схема SCHEMA, таблица TABLE_NAME). Гранулярность: одна строка = [grain]. Хранит [назначение]. Также известна как: [синонимы/сокращения]. В отличие от [похожая таблица, если есть] — [граница охвата].»

Запрещено:
- Дублировать полный список колонок в text — это покрывает детерминированный COLUMNS-тулз
- Копировать сырые примеры данных в text целиком (1–2 показательных значения как иллюстрация — допустимо, не более)

Bridge-блок (см. п.9) сюда не нужен по той же логике, что для business_scenario/metric — естественное описание таблицы уже близко к тому, как формулируется запрос на её поиск.

---

## 5. Бизнес-сценарий (business_scenario)

**text:** какую бизнес-задачу решает запрос — домен, сущность, разрез, бизнес-условие отбора (переформулированное из WHERE), явные измерения с привязкой к идентификатору («в разрезе категории товара (CATEGORY_ID)»).
**extra_json:** `{"domain": "...", "source_tables": [...], "dimensions": ["CATEGORY_ID", ...]}`

Запрещено: построчный пересказ SQL; голые имена таблиц/колонок без бизнес-расшифровки.

---

## 6. Бизнес-метрика (metric)

**text:** что измеряет метрика, способ агрегации словами, гранулярность результата, единица измерения (только если однозначна), бизнес-условия, влияющие на значение.
**extra_json:** `{"granularity_columns": [...], "source_tables": [...], "formula_hint": "SUM(...)"}` — точную формулу как код держать только в extra_json, если она нужна машинно.

Запрещено: путать с SQL-правилом (метрика — про ЧТО и ПОЧЕМУ, не про детали JOIN); код формулы в text.

---

## 7. SQL-правило (sql_rule)

**text:** естественно-языковое объяснение неочевидной логики без синтаксиса кода. Пример:
> «Активным клиентом считается тот, у кого дата последней операции (LAST_OPER_DT) не более 90 дней до текущей даты, и статус счёта (ACCOUNT_STATUS) равен значению "активный". Это правило применяется при расчёте [метрика/сущность].»

**extra_json:** `{"sql_fragment": "CASE WHEN account_status = 'ACTIVE' AND datediff(current_date, last_oper_dt) <= 90 THEN 1 ELSE 0 END", "source_tables": [...], "columns": [...]}`

Если в запросе несколько правил — отдельный чанк на каждое, не смешивать.

---

## 8. SQL-пример (sql_example)

**text:** естественный вопрос, который реализует запрос (как сформулировал бы конечный пользователь) + краткая аннотация паттерна, бизнес-нейтрально вперёд, если паттерн универсален:
> «Скользящее среднее (rolling average) за 7 дней — паттерн сглаживания временного ряда через оконную функцию. Пример применения: выручка (REVENUE) по категориям товара (CATEGORY_ID) в домене Магазин.»

**extra_json:** `{"sql_query": "...", "source_tables": [...], "semantic_key": "...", "query_type": "..."}` — последние два поля переиспользовать из вашего sqlglot-пайплайна (структурный фингерпринт/семантический ключ), а не генерировать заново через LLM.

Запрещено: вопрос как буквальный перевод SQL; SQL-синтаксис в text.

---

## 9. Bridge-блок — только для sql_example, одна строка

Применяется выборочно: business_scenario и metric уже естественно близки к формулировке вопроса (добавление переформулировки туда избыточно и только размывает вектор); sql_rule, как правило, описывает доменное правило, а не переиспользуемую технику, поэтому не нуждается в этом по умолчанию.

Для sql_example — добавлять одну дополнительную строку в конец text: доменно-нейтральный кластер названия техники (RU+EN), без слов-типов («пример» и т.п., это покрыто `chunk_type`) и без доменных терминов основного текста. Цель — поймать под-запросы агента, где домен в декомпозиции вообще отсутствует.

Пример (sql_example для скользящего среднего выручки по категориям в Магазине):
> Основной text: «Скользящее среднее (rolling average) за 7 дней — паттерн сглаживания временного ряда через оконную функцию. Применяется к выручке (REVENUE) по категориям товара (CATEGORY_ID) в домене Магазин.»
> + bridge-строка: «скользящее среднее rolling average оконная функция»

Соответствующий вызов тулза агентом: `search_semantic(query="скользящее среднее 7 дней rolling average выручка категория", chunk_type="sql_example")` — type-слово ушло в параметр, в `query` его нет.

---

## 10. Формат вывода LLM

```json
{
  "chunks": [
    {
      "chunk_type": "table",
      "text": "...",
      "extra_json": {"schema": "...", "table_name": "...", "domain": "...", "grain": "..."}
    },
    {
      "chunk_type": "business_scenario",
      "text": "...",
      "extra_json": {"domain": "...", "source_tables": [], "dimensions": []}
    },
    {
      "chunk_type": "metric",
      "text": "...",
      "extra_json": {"granularity_columns": [], "source_tables": []}
    },
    {
      "chunk_type": "sql_rule",
      "text": "...",
      "extra_json": {"sql_fragment": "...", "source_tables": [], "columns": []}
    },
    {
      "chunk_type": "sql_example",
      "text": "...",
      "extra_json": {"sql_query": "...", "source_tables": [], "semantic_key": null}
    }
  ]
}
```

Инструкция LLM: если для какого-то типа в данных недостаточно информации — не включать объект в массив `chunks` вовсе (не генерировать пустые/предположительные значения).

---

## 11. Открытый архитектурный вопрос (не промпт, к размышлению)

Если один и тот же универсальный SQL-паттерн (rolling average, ranking и т.п.) повторяется в sql_example чанках для многих доменов/таблиц, доменно-нейтральный технический запрос будет конкурировать с десятками похожих чанков. По аналогии с выводом COLUMNS/JOIN в детерминированные тулзы — возможно, стоит завести структурированный тег `sql_pattern` (window_function / rolling_average / dedup / pivot) как metadata-поле для предварительной фильтрации, аналогично `chunk_type`.

---

## 12. Сохранение собственных имён и литералов (RU-генерация из EN-промпта)

**Проблема:** при инструкции «пиши на русском» LLM иногда переводит/транслитерирует имена собственные и литералы (бренды, организации, enum-значения типа `Premium`), хотя они должны оставаться как есть — это не стилистический, а функциональный риск: если literal в тексте чанка не совпадает с реальным значением в БД, downstream text2sql-генерация теряет точность.

**Решение — маркировка на входе, не угадывание моделью:**

1. На препроцессинге оборачивайте все proper nouns/литералы из метаданных (имена таблиц/брендов/организаций, enum-значения, коды) в маркер перед вставкой в промпт: `` `Premium` ``, `` `SuperFoods` ``. Вы заранее точно знаете, что является литералом, а что обычным текстом — не нужно, чтобы это угадывала модель.

2. В промпт (EN) — явное правило:
```
CRITICAL — literal values and proper nouns:
Any text wrapped in backticks (`...`) in the input is a literal value,
identifier, or proper noun that MUST appear in your Russian output
EXACTLY as written — never translated, transliterated, or grammatically
inflected, even if it's a common English word with an obvious Russian
translation.

Example:
Input: segment = `Premium`, store = `SuperFoods`
Correct:   ...для клиентов с сегментом `Premium` в магазине `SuperFoods`...
Incorrect: ...для клиентов с премиальным сегментом в магазине Супер Фудс...
```
Backticks из финального текста чанка убираются постобработкой — это сигнал для модели, не часть итогового text.

3. **Детерминированная проверка после генерации** — обязательный шаг, не опциональный: каждый защищённый литерал (из исходных метаданных, до оборачивания) должен находиться verbatim в выходном тексте; если не найден — триггер регенерации. Аналогично существующему паттерну калибровки через LLM re-synthesis.
